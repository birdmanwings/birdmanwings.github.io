端侧大模型推理引擎剖析（一）｜推理流程总览

bdwms
2026-11-15
llama.cpp
推理引擎

The main goal of llama.cpp is to enable LLM (and VLM) inference with minimal setup and state-of-the-art performance on a wide range of hardware … 项目 README

模型架构规定了一次前向计算所需的运算及其数据依赖。推理引擎负责将这些运算映射到具体硬件，在设备的算力、内存带宽和容量约束下，安排权重的存放、算子的执行与中间结果的复用。

本系列以 llama.cpp v1.0.0 为基础，分七篇讨论端侧推理引擎的设计与实现。第一篇从模型加载讲到逐步生成，梳理一次前向计算在整个生成过程中的位置，并结合实测分析各阶段的耗时与内存占用。

虚线标出第一篇与后续各篇的总分关系。实线沿执行过程展开，末尾两条分支分别给出下一轮前向所需的历史 K/V 和新 token。

一次前向的计算图

给定一串输入 token，自回归语言模型经过多层运算，在末位置得到词表中各候选 token 的分数（logits）。从输入算到这些分数，就是一次前向。

以自注意力层为例，查询 Q、键 K 和值 V 是输入 X 的三个矩阵投影。三者可以独立求值，每个投影内部的矩阵运算也可以并行。

Q = XWQ，　K = XWK，　V = XWV

图中节点表示运算，箭头表示数据依赖。计算注意力权重需要 Q 和 K，加权汇总还需要 V。把一轮前向中的运算按这种依赖关系连起来，就得到一张有向无环图（DAG）。

计算图规定了哪些结果必须先就绪。要在端侧设备上执行这张图，引擎还要决定权重放在哪里、每段计算交给谁，以及哪些中间结果可以共用一块内存。

从计算图到端侧硬件

硬件约束与评价维度

仍以投影为例。处理整段提示词时，多个 token 的向量可以一起乘以同一组权重，GPU 有较多可并行的计算。逐个生成时，单个请求每步只增加一个位置，各层权重仍要参与运算。此时即使计算单元充足，从内存读取权重的带宽也可能限制生成速度。

还有一项更直接的约束是容量。Mac 和 Jetson 的 CPU、GPU 共享系统内存。模型权重占用一部分容量，生成时保留的历史 K/V 和临时工作区也需要空间。若采用更低精度的权重或 KV 缓存，存储和读取的数据量可以减少，模型的预测也可能随之改变。由此可以从三个维度评价一次设计选择。

评价维度 具体看什么
时间 从发起请求到首个 token 的等待（TTFT），以及首个输出之后，每生成一个 token 的平均耗时（TPOT）。把计时起点放在程序入口，则还会计入模型加载等一次性开销。
空间 权重占多少，跨轮保留的 KV 缓存占多少，执行中间结果还需要多大工作区。
质量 固定评测语料或任务，比较改变数值表示前后，对同一前缀的预测或任务得分有何变化。

引擎的设计选择与分层

以图中的查询投影为例。GPU 的并行算力能否用上，取决于后端是否支持这项运算，以及输入和权重能否及时到达。顺着这层投影，可以区分引擎的三种设计选择。

设计选择 在一层投影中如何体现
放置 根据 CPU、GPU 的算子支持、计算能力和可用容量，选择由哪个设备执行投影、权重存放在哪类缓冲区。
调度 按后端切分计算图，为跨后端依赖安排必要的搬运与同步，并按中间结果的使用时序规划工作区复用。
表示 选择权重和 KV 缓存的数值格式。量化可以减少存储和读取的字节数，也可能改变预测结果。

在 llama.cpp 中，模型计算的描述与后端执行分属两层。应用通过 llama.h 使用推理库。libllama 描述 Qwen3 所需的权重，并用这些权重构建计算图。libggml 提供张量、算子和后端调度接口，具体内核由相应后端实现。以图中的查询投影为例，Mac 和 Jetson 可以共用 Qwen3 的建图代码，执行时分别使用 Metal 和 CUDA。这也是 v1.0.0 强调库接口与兼容性的背景。v1.0.0 发布说明 · Qwen3 建图源码

从一次前向到连续生成

llama-simple 是一个最小的文本生成程序。它读入模型文件和一段提示词，逐个输出后续 token。从它的 main 可以看到，模型文件中的权重如何成为计算图的输入，一轮前向留下的状态又怎样被下一轮使用。

  1. 从文件到模型。GGUF 文件记录了模型架构、配置参数和各层权重。加载器据此建立 llama_model，并将权重映射或读入后端可访问的缓冲区。此后，建图代码可以通过模型对象取得每一层所需的权重。

  2. 从模型到上下文。llama_context 管理执行一次前向所需的资源，也保存跨轮使用的状态。本例在创建上下文时为历史 K/V 预留缓存。为了确定计算工作区的大小，引擎还会在 sched_reserve 中按预期输入规模构建逻辑图，由调度器按后端切分，并根据中间结果的生命周期规划内存复用。这些准备在提示词参与计算之前完成。

  3. 从输入到前向结果。提示词分成一串 token 后，第一次调用 llama_process 处理整段输入（prefill）。引擎为这批输入构建或复用计算图，调度器将各子图交给相应后端执行。前向完成后，末位置的 logits 可供采样，提示词各位置的键和值则留在 KV 缓存中。

  4. 从采样到下一轮前向（图中第 4、5 步）。本例的采样器选择分数最高的 token。若选中普通 token，程序将其输出。只要还需继续生成，就把它作为下一轮唯一的新输入，沿用历史 K/V 再做一次前向（decode），得到下一组 logits。循环在采到结束标记或达到输出上限时终止。llama-simple 生成循环

实践：耗时与内存分析

实验环境

两端运行同一份 Qwen3-4B Q4_K_M 权重和同一版本的 llama-simple（v1.0.0，b1b770d90，Release）。日志记录的 37/37 层均放在 GPU 上。输入、生成上限和贪心采样策略相同，这组实验比较时间与空间。

环境 Mac mini Jetson Orin Nano Super
硬件与系统 M6，24 GiB，macOS 27.2.1 Orin，8 GB，Ubuntu 22.04.5，L4T 36.4.3，MAXN_SUPER
后端与加载方式（auto） Metal，mmap，模型位于外置 SSD CUDA 12.6，none
采集工具 Instruments · Metal System Trace Nsight Systems 2024.5.4

从启动到首个输出

每台设备连续启动两个新进程，两次之间保留系统页缓存。从进入 main 开始计时，到首个新 token 输出为止。这个口径包含后端准备、模型加载、上下文创建和首次前向。

运行 加载模型 创建上下文 到首个输出
Mac 第一次 2.75 s 14 ms 7.63 s
Mac 第二次 0.15 s 13 ms 0.25 s
Jetson 第一次 7.98 s 69 ms 8.39 s
Jetson 第二次 6.07 s 51 ms 6.38 s

Mac 第一次运行时，准备 Metal 算子库单项就用了 4.78 秒。第二次，这项工作降到 14 ms，加载模型也从 2.75 秒降到 0.15 秒。Jetson 第二次的 6.38 秒里，6.07 秒仍在模型加载阶段，上下文创建只用了 51 ms。要把这 6.07 秒进一步分到读文件、缓冲区准备和权重传输，还需要在加载器内部分段计时。

模型就绪后的前向耗时

本次提示词分为 4 个 token。一次 prefill 后就能采样出首个输出，余下 15 个输出各需一次 decode。下表取自两端各一次普通运行的引擎计时，GPU 时间线按相同参数另行采集。

阶段 Mac Jetson
Prefill（4 个输入 token） 42.28 ms 236.10 ms
Decode（15 步合计） 312.65 ms 1030.78 ms
Decode（平均每步） 20.84 ms 68.72 ms
采样（16 次合计） 0.88 ms 5.11 ms

在这次 4 个输入、16 个输出的短请求中，15 步 decode 占前向总耗时的 88.1%（Mac）和 81.4%（Jetson）。这里的分母是 prefill 与 decode 之和。逐步生成占比高，既与单步成本有关，也与它连续执行了 15 次有关。若要改善首个输出之后的生成速度，表中的单步 decode 耗时比启动耗时更有参考价值。

图 1　Mac 上的 Metal 前向计算时间线
选中的 Compute 命令耗时 5.11 ms。按执行顺序推定，prefill 对应前两条 Compute 命令，累计 32.42 ms。

图 2　Jetson 上的 CUDA 内核耗时分布
四种 mul_mat_vec_q 内核合计占本次采集全部 GPU 内核累计执行时间的 88.4%。

内存的分配时机与占用

先按创建时机看。模型加载时建立权重缓冲区，创建上下文时再为 KV 缓存与计算工作区预留内存。随后每轮前向往缓存里写入新位置的 K/V。因此在时间线上，KV 缓存已经分配时，提示词对应的 K/V 可能还没有写入。

用途 Mac Jetson
权重（设备侧 / 主机侧） 2375.91 / 304.28 2375.91 / 304.28
KV 缓存（设备侧） 36.00 36.00
计算工作区（设备侧 / 主机侧） 5.38 / 0.16 2.48 / 0.16
输出缓冲区（主机侧） 0.58 0.58

表中数值是引擎报告的缓冲区容量，单位为 MiB。本例预留 256 个上下文位置，设备侧权重为 2375.91 MiB，约是 KV 缓存的 66 倍，明显大于计算工作区。若保持模型和缓存格式不变，增加预留位置，权重大小保持不变，KV 缓存的容量则会增长。Jetson 的进程峰值 RSS 为 548.82 MiB，未覆盖全部 CUDA 分配。这里以引擎的缓冲区记录衡量设备权重占用。

图 3　Mac 上的模型权重映射
3.690 s 处创建的 Metal 缓冲区大小为 2.32 GiB。调用栈显示，load_tensors 经由 ggml_metal_buffer_map 映射权重。

图 4　Jetson 上的 CUDA 内存分配时序
设备权重（2375.91 MiB）分配于 1.871 s，KV 缓存（36 MiB）分配于 9.160 s，随后分配计算工作区。

总结

一次文本生成从加载权重开始，经建图、调度与执行得到候选分数，再由采样把本轮输出接回下一轮输入。沿这条路径，放置决定数据与计算的位置，调度安排子图执行与内存复用，表示决定权重和 KV 缓存采用何种数值格式。时间、空间和质量则用来评价这些选择的代价。

本篇固定模型与数值格式，先观察时间和空间。Jetson 第二次启动时，等待首个输出的时间主要花在模型加载。模型就绪后，两端大部分前向时间花在随后的 15 步 decode。在只预留 256 个上下文位置的配置下，设备侧内存占用以权重为主。后续比较量化方案时，还需在同一份语料上考察预测质量。

回到前面的查询投影，建图时已经可以从 llama_model 取得它的权重。加载器怎样在 GGUF 文件中定位这个张量，又怎样让后端访问它的数据？Mac 和 Jetson 都由 CPU、GPU 共享物理内存，两者的加载路径在哪一步分开？第二篇《从 GGUF 到内存》将跟随这个张量，从它在文件中的位置一直看到它在内存中对应的权重缓冲区。
